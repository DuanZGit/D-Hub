# code-archaeology

三件事，按需取用，不必全做。核心纪律：**考古结论要有 commit 佐证，不许凭代码形状猜意图。**

## 1. Git 历史考古——分清三类代码

改动前先跑（路径换成目标文件）：

```bash
git log --follow --oneline -- <file> | head -30        # 文件级历史
git log -L <start>,<end>:<file> --oneline              # 函数级历史
git blame -L <start>,<end> -- <file>                    # 行级归属
```

对可疑代码段，找它诞生的 commit 读当时的 commit message 和关联 issue/PR：

- **有意设计**：有明确 commit message 说明取舍、关联 issue/PR、或后继 commit 反复围绕它演进
  → 保留，改动前先理解约束（"为什么"比"是什么"重要）。
- **历史遗留**：早期写的、后来没人动、无 message 说明、与现状脱节
  → 标记候选清理项，报告给用户，**不擅自删**。
- **失效问题**：当初为修 bug/绕限制打的补丁，前提条件后来已消失
  → 提出移除方案，注明依赖它的隐藏耦合，让用户拍板。

*完成判据*：每个"能不能动"的判断都有一句 commit 佐证（hash + 当时为什么写它）。

## 2. 新工程师视角——评认知成本

假设接手的是一个很强的新工程师，第一周要上手这段代码：

- 通读主流程，标出让他皱眉的点：命名与行为不符、抽象过度（跳三层才到逻辑）、
  职责不清（一个函数干三件事）、重复模式没收敛、魔法数字/隐式约定。
- 每个痛点给出**具体简化方案**（改成什么、删什么），按「认知成本 ÷ 改动风险」排序，
  高成本低风险的排前面。
- 只提方案不动手，除非用户明确要求重构。

## 3. 近期 PR 复盘——找最慢环节

用户要"分析最近的 PR / 为什么迭代慢"时：

```bash
git log --since="30 days ago" --merges --oneline | head -20   # 时间窗自己调
gh pr list --state merged --limit 30 --json number,title,createdAt,mergedAt
```

- 用 createdAt→mergedAt 算各 PR 停留时长，排出最慢的 3-5 个。
- 逐个看卡在哪：review 等待轮次、CI 失败重跑、改动面太大拆不动、返工重做。
- 输出：最慢环节排序 + 每项一个可执行改进（如"改小 PR 粒度""CI 分层快慢道"），
  不写泛泛的"加强沟通"。

## 触发边界

- 用户只要"解释这段代码"（不涉及能不能动/历史）→ 直接答，不用本技能。
- 改动本身 → 回到 ponytail（最懒可行方案）；考古只是动手前的侦察。
- 产物要落盘时按 D-Hub 惯例写 `docs/`，不额外建目录。

# DK 决策模型

> DK 的**通用决策框架**——不是只选品。食品/健康/买/换/选/取舍（A vs B）共用同一套判断。
> 核心：**安全 VETO → 价值判断 → 频率触发器 → 信号集与证据 → 地域可得性**，并带**进化闭环**。
> 用户：断就（base 杭州）。与 cook 的 [factor-model.md](factor-model.md) 同源——都是"因子×场景→可预期结果"。

## 决策漏斗（先砍范围，再深挖）

选品/决策面对海量候选（一个品类可能上千 SKU），**不穷举，用漏斗层层砍**：

```
需求（这个家怎么用） → 用户给的使用场景
  ↓ ① 地域/可得性：base 杭州，优先国内在售（淘宝/京东能买）
  ↓ ② 预算带：按用户的价值判断设价格区间（价格是约束，不是目标）
  ↓ ③ 市场验证：京东/淘宝该品类【销量 + 好评率】TOP（用钱投票，最大的一刀）
  ↓ ④ 人群共识：什么值得买 / 知乎 / 小红书 / B站「XX推荐」榜单 → 候选来源（不爬全站 SKU）
  ↓ ⑤ 幸存 5–10 个，各自抓【决策关键参数】→ 跑完整思维链
```

**关键**：大众和市场已经帮你筛剩十几个，从这其中按用户规则挑，而不是穷举比较。
涉及多方案决策时，直接交付**交互式决策台 HTML**，方便用户在本地点击决策并复制开工指令。

## 选品渠道硬门槛（不可跳过）

只要任务属于**商品选购/购买决策**，以下两个内容渠道都必须检索：

- **B站**：找综合横评、选购建议、单品实测；每个关键视频都要分别读取**字幕/正文**和**评论区**。
- **小红书**：找真实用户体验、长期使用、踩坑和价格/购买记录；每个关键笔记都要分别读取**正文**和**评论区**。

两类内容承担不同职责：

| 内容 | 主要回答 | 风险 |
|------|----------|------|
| 视频/笔记正文、字幕 | 作者测了什么、参数如何、结论是什么 | 可能送测、恰饭、选择性展示 |
| 评论区 | 用户是否复现、长期是否稳定、真实缺点、价格和售后坑 | 样本偏差、极端个案，不能单条定论 |

**执行规则**：
1. 先在 B站和小红书各搜一轮，优先综合横评/选购建议，再补单品实测。
2. 每个平台至少保留：1 个横评/选购类内容 + 1 个单品或长期使用内容；候选发生争议时继续扩充样本。
3. 正文和评论区必须分别记录，不能用“看过视频/笔记”代替评论区取证。
4. **渠道失败必须明示**：B站或小红书不可用时，只能标记“单渠道证据”，不得宣称完成双渠道验证；应改用另一渠道、网页或电商评论补证。
5. 弹幕不是硬门槛：B站工具能稳定取得时可作辅助信号（`api.bilibili.com/x/v2/dm/web/seg.so` 按 segment 抓、统计品牌提及频次），但不能用弹幕替代字幕或评论区（弹幕是即时反应，评论是使用反馈）。
6. 价值结论至少经过“B站正文/评论 + 小红书正文/评论”四格证据矩阵中的三格；关键推荐最好四格齐全。

## 思维链（每个候选跑一遍）

```
① 安全 VETO（最高优先）：人身 / 食品 / 使用安全
   → 只走权威/循证（WHO/卫健委/GB标准/制造商安全参数）
   → 威胁安全 → 直接出局，不看价格、不看体验
② 价值判断（核心轴）：多花的钱，能不能换来【真实体验提升】？
   能（用得好了 + 有技术壁垒 + 高频离不开）→ 一步到位买贵的
   不能（无壁垒 / 只加参数不加体验 / 可短时替换 / 低频）→ 买便宜的，能换就换
   → 跨境/海淘在价值判断里扣分（售后 / 保修 / 物流折损）
   → **新旧/迭代维度**：默认「选新不选旧」（新品=更新工艺/更强参数/更长售后周期），
     但**旧款若口碑特别好且持续被验证**（销量长期靠前、多年仍是该档标杆、社区长期热议），
     可**抵消「旧」的减分**。新旧是权重不是一刀切；口碑持久度能抵消年份。
     ⚠️ 判断"持久口碑"需看跨年销量/评测是否持续，而非单一爆款热度（避免被一轮营销带偏）。
   → **价格敏感/锚点**：用户"哪个便宜买哪个"是合理默认（同类差价大 → 偏便宜款，
     贵的要有明确体验提升才追）。⚠️ 但**历史低价是锚点不是现价**：
     见过大促价（如 618 ¥4xx）后对日常价（¥686）"不舒服"是锚定效应——
     决策用**当前到手价 vs 功能差值**；要蹲价就明确设目标价（如"≤¥550 买幻刺，
     否则 398 买巫师 Z Pro"），把"等不等"变成可执行规则而不是心理别扭。
③ 频率触发器：高频 + 离不开 → 才进入②（频率不是独立轴，是喂给②的触发器）
④ 信号集：参数 + 使用体验 + 技术含量 + 口碑
   → 渠道：博主测评 + 评论区真实反馈
   → 反恰饭：「靠多看」——多来源交叉、看真实差评/缺点、看是否真解决日常痛点
   → 安全感不走这里（走①循证）
⑤ 地域/可得性：强偏好国内，可接受跨境但折损
```

## 双轨证据政策（关键）

| 判断类型 | 信源 | 依据 |
|----------|------|------|
| 安全 | 权威/循证（WHO/卫健委/GB/制造商安全参数） | 错误代价是身体，必须最可靠 |
| 价值（好不好用 / 值不值） | KOL 测评 + 评论区 | 用户真实方法，"靠多看"量变出真 |

**两者冲突 → 安全 VETO 压过价值**，哪怕它便宜又好评。

## 验证层：独立第二评委交叉验证（可选）

> ✅ 2026-11-03 升级：**TypeSafe System One（THX-01）** 经 `api.hal-x.ai` 免 Key 零样本决策端点调用，客户端
> `scripts/jev-judge.py`。协议：`POST https://api.hal-x.ai/v1/systemone`，
> body `{"state", "questions": {名: {type, question, criteria}}}` → `answers` + `usage`。
> 工具换、纪律不换：只进价值侧、分数是意见不是证据、安全 VETO 绝不外委。

思维链跑完、出推荐之前，把结果交给独立第二评委交叉验证：

```bash
# state=候选+决策关键参数+用户标准（去掉安全项）；questions 把决策标准逐条编码
# 默认使用 SemIf（JevBench 开源榜首 74.6，软概率校准最佳）
echo '{"state":"<候选与参数>","questions":{
  "which":{"type":"choice","instructions":"该选哪个？","criteria":{"A":"...","B":"...","neither":"都不合适"}},
  "value_gap":{"type":"score","instructions":"A 相对 B 的提升配得上差价吗？","criteria":["完全配不上","略不值","基本值","明显值"]},
  "high_freq":{"type":"noul","instructions":"这是高频场景吗？"}
}}' | python3 scripts/jev-judge.py
```

三种 question 对应原 `select`（choice 多候选终审）/ `compare`（score 打分 tie-break）/ 封闭判断（noul 概率）。
响应带 `probabilities` + `confidence`，比单一结论更适合交叉验证。

**三款模型（2026-10-08 前免费，到期后需重新评估）**：

| model id | 架构与基准 | 实测行为（2026-09-26） | 定位与建议 |
|---|---|---|---|
| **`SemIf`** | Qwen3.5-4B 冻结 + Logit 直读<br>JevBench 74.6 分（开源第一） | 四位浮点细腻连续，能精准反映不确定度（打分犹豫时 confidence 可低至 0.20） | 🏆 **默认主力首选**：负责常规终审与所有 tie-break 打分 |
| **`Kev-4B`** | Qwen3.5-4B + LoRA + Pointer Head<br>JevBench 62.2 分 | 分布平滑保守（confidence ~0.51），偏均值回归 | 🥈 **双评委交叉**：重大取舍或犹豫局拉进来对照 |
| **`diffusiongemma`** | Gemma 基座 + 扩散头 | 极端 one-hot（非 0 即 1），无置信度过度 | ❌ **不作主力**：丢掉了软概率与犹豫度信号，仅作二值硬分类对照 |

- **默认主力首选**：使用 `THX-01`，响应约 30ms，零样本分类与打分，返回软概率与置信度。
- **免 Key 免计费**：直接走 hal-x 公共网关，不依赖硅基流动 API Key，无余额扣减风险。
- **降级机制**：若网络不可用或 API 故障，自动跳过验证层，依靠主流程思维链输出，绝不阻断决策。

**红线**：
- verifier 只进**价值侧**（哪个好用/更值），分数是**意见不是证据**，定位是交叉验证/tie-break
- **安全 VETO 绝不交给 verifier**——安全仍只走权威/循证（双轨证据政策的硬边界）
- criteria 由 [决策检验] 积累的真实权重持续校准，验证器越用越贴用户

**调用纪律（2026-08-28 教训）**：盲评去品牌价格、criteria 写成可逐条判定的精确定义、M3 离散分分差 <0.05 视为噪声、快速 400 = MiniMax 限流。原收编于 Gene-005，该 Gene 机制已于 2026-09-04 废弃（`shared/evolution-deprecated-20260904/genes/Gene-005.md` 存档），纪律现就地内联于本节。

## 具体参数怎么抓（决策关键参数 + 标称/实测分离）

**价格/销量取证（简单拉取即可，不硬闯电商登录墙）**：
- 京东/淘宝 web 端对未登录 WebView 风控极严（search 直接跳验证码/登录页），**不要反复尝试硬闯**
- 实际做法：①百度/Google 快照搜"品牌+产品名+价格"拿参考价（标注单源）②xhs/评论区里的价格提及作旁证 ③最终价以用户自己点开 App 看到的为准
- 销量 TOP 初筛失败时，改用"B站横评高频出现 + xhs 高赞"做市场验证替代，报告里注明"电商平台销量未取证"

1. **先定义这个品类的「决策关键参数表」**——只抓影响"真实体验"的那几个参数，不全量抓。
   - 例：磨豆机 = 磨盘材质 / 研磨均匀度 / 电机功率+噪音 / 清洁难易 / 刀头结构。
   - 原则：**参数喂给②价值判断，不是给用户看一堆规格**。
   - 进阶版参考：一份好的横测表（如某测评 KOL 的实测对比）已按"决策关键参数"筛好，
     可直接作为**双轨证据中的实测层**（标称 vs 实测、同条件横向可比）。
     ⚠️ 横测表要区分**可比参数**（研磨时间/重量/档位——跨品牌可比）
     与**不可比参数**（各品牌的"刻度值/研磨度数字"——刻度体系不同，别硬比）。
2. **金字塔取证**：
   | 层级 | 来源 | 价值 |
   |------|------|------|
   | 官方 | 官网 / 规格书 | 标称值，可信但带营销水分 |
   | 电商 | 京东 / 淘宝详情页「规格参数」 | 结构化参数，快速拿全 |
   | 实测 | B站 / 小红书正规测评 | **标称 vs 实测偏差**、真实使用 |
   | 口碑 | 评论区 | 前面看不到的坑 |
3. **评论区抽样（价值侧的关键一环，别跳过）**：
   - 🎯 **横评/选购建议类视频/笔记的评论区**最有价值——用户在那里问真实问题、
     老用户现身说法（"用了 N 年换 X 感受明显"），比测评正文更能反恰饭
   - 渠道：B站 `bili video <bvid> -c`（评论）· 小红书 `xhs comments <完整note_id> --xsec-token <token> --all`（--all 真实存在，v0.6.4 已验证）
   - ⚠️ xhs CLI 调用纪律见下方专门小节，**先读再调**，别现场试错
   - 评论区意见要做**信号统计**：同一观点出现次数 ≥2 才进决策参数（如"幻刺太干净对普通豆是劣势"多人认同）
   - 对照送测风险：评论区有人点破"评测都是品牌送测"时要警惕测评正文，转向评论区找反方意见
4. **标称值 vs 实测值分开记**，决策用**交叉后的可信值**，标置信度；多源不一致时降到"待确认"给区间。

### xhs CLI 调用纪律（2026-09-07 洗发水决策踩坑固化）

> 三类事故全踩过：臆造参数、截断 ID、风控后连打。照做，别现场试错。

1. **参数以 `--help` 为准**：`search` 翻页是 `--page N`（**无 `--limit`**）；`comments` 有 `--all`。
2. **完整 32 位 ID + 配对 token**：token 取 search 结果里每个 item 的 `xsec_token`，与该 item 完整 `id` 一一配对。截断 ID 或 A 的 token 配 B 的 ID → `Could not resolve xsec_token`。展示可短 ID，调接口必须原样配对。
3. **风控处理**：见 `Captcha required`/`empty noteDetailMap`/`Request failed after 3 retries` = 已触发。
   - ✅ `delay` ≥120s 冷却 → 单条重试一次 → 再败放弃换信源；❌ 连续重试只会加深风控
   - 🔓 **解除靠换 session 不靠冷却**（标记挂 cookie 上）：让用户从已登录浏览器 F12 复制**完整 cookie 串**，写入 `~/.xiaohongshu-cli/cookies.json`。必需 `a1`/`web_session`，**且必带** `websectiga`/`sec_poison_id`/`id_token`/`webId`/`gid` 等指纹字段——只给 a1+web_session 四件套会报 code=-3「薯队长遇到小麻烦」。写完 `xhs status` 验证。（code=-3=风控/会话错，-100=session 过期）
4. **接口脆弱度** `search` > `comments` > `read`：`read` 最易 empty noteDetailMap，正文拿不到就用 search 摘要（display_title+interact_info）+ comments 顶上，证据链不断。批量抓取写脚本循环（每条 sleep 20–30s），别手敲。输出默认 YAML，`--json` 才是 JSON，解析前 `raw.find('{')` 截（stdout 混 WARNING 行）。

## 进化闭环（核心增量，区别于一般技能）

```
DK 给报告 → 用户给真实思路 + 最终决定
  · 一致 → 标 [决策检验 YYYY-MM-DD]
  · 不一致 → 剖析差在哪（用户真实权重 / 我漏判的变量）→ 调整规则 → 链条进化
  · DK 可反过来「劝」用户（我的链有道理）→ 也算进化
决策日志累积，随使用越用越准。
```

**统一检验标记**：做菜用 `[实战检验]`，决策用 `[决策检验]`——同一套"随使用变强"的机制，不另立一套。

**经验沉淀约定（原 Gene 卡机制已废，2026-09-07 经 verifier 裁决降级为 OpenViking 写入约定）**：
- 教训/决策检验写进 OpenViking（`remember`），**不另建卡系统**（状态机/逐卡 git/变更门全部废弃）。
- 但保留 Gene 的内核：每条经验写成 `触发场景 → 动作 → 验证方式` 的结构化条目，别灌散文——语义召回靠这个结构才取得准。
- **跨场景复现才信任**：单案例只算"试用"，第二次不同场景复现才当可靠规则；被证伪就改写或删。

## 反模式

1. ❌ 全量抓参数再让用户自己挑（违背"决策关键参数"原则）
2. ❌ 把博主/评论区用做**安全**依据（安全只走权威，走①）
3. ❌ 用一个固定答案收尾，不展示完整思维链（用户要的是"完整推演报告"）
4. ❌ 跨境/海淘不标售后/保修折损（地域可得性扣分）
5. ❌ 处理决策时忽略用户的进取心/偏好，变成"全网最佳"通用推荐（就事论事，基于用户真实约束）
6. ❌ 决策后不落 `[决策检验]`、不对比用户真实想法（进化闭环失效）
7. ❌ 把 llm-verifier 分数当证据、或用它做安全判定（verifier 只进价值侧，安全只走权威）
8. ❌ 把"选新不选旧"当铁律一刀切，忽略口碑持久的旧款标杆（违背新旧权重原则——见②）
9. ❌ 推荐时只甩规格参数表，不给"这个参数对真实体验意味着什么"的解读（决策关键参数原则——参数是喂给②的判断，不是给用户看的数字堆砌）
10. ❌ 最终推荐不给**横向对比表**（候选×决策关键参数逐格）+ **逐条数据源引用**（B站 bvid/笔记 id/电商页/横评图出处 + 置信度）。用户要能自己核验每一格，不可审计的证据链=没有证据链（2026-08-27 磨豆机单被用户点名）
11. ❌ 用户自带证据（截图/横评图/朋友推荐）被忽略或直接采信——必须**先反查出处**（如"横评图来自B站哪个视频评论区"→定位原视频→补正文+评论四格取证），出处不明的证据标"待确认"参与决策但降低权重
12. ❌ llm-verifier 未实际调用成功却在报告里暗示"已交叉验证"——verifier 调用失败/超时必须在报告里明示"未经独立验证"，不能静默跳过

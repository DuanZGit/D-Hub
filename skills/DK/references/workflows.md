# DK 工作流详解

> SKILL.md 引用。包含五个子工作流：晚餐合集生成、营养估算、食材库存同步、实测反馈修订、决策与取舍。
> 规则已收敛到当前状态；历史变更见 `wiki/log.md`。

## 通用家庭基准（所有工作流共用，静默套用勿反复复述）

- **做饭**：每道菜按 1 份的实际食材量做（断就 + 小豆两人吃）
- **分食**：1 份菜总热量按 3 等分——断就当晚 1/3、小豆当晚 1/3、小豆次日午餐带饭 1/3
- **米饭**：3/4 碗/人
- **营养档案**：`raw/misc/小豆-用户营养档案.md`（双人，含 BMR/TDEE 预计算，直接查表勿重算）
- **库存文件**：`raw/misc/小豆-家庭食材库存.md`

## 一、晚餐合集生成工作流

**触发**：用户说"今晚做 X / Y / Z"或"给我拼菜单"。报菜后输出合集，**优先给出极简操作清单**（备料克重、下锅顺序、火候时间、避坑防烫），科学原理解释收拢到文末。即使只有 1 道菜也是默认动作，不要问"要不要生成"。

### 工作流（6 步）

1. **需求澄清**：挑关键问（忌口/器具/食材厚度部位如"上脑牛排 M3 0.8cm"），能推断的用默认值

2. **原料对账**（必做）：读库存文件 → 比对用户报的菜 → 列出**缺口** → 让用户决定取消/替换/等买。不静默修改

3. **每菜因子卡生成**：
   - 先查 wiki 已有该菜谱 → 复用
   - 没有 → 按 docs/factor-model.md 新建 `raw/recipes/YYYY-MM-DD-菜名.md`
   - 用 `scripts/wiki-to-html-v2.py` 生成 HTML 因子卡 → `$WORKSPACE/{菜名}.html`

4. **晚餐合集 HTML 生成**（关键交付物）
   - **单一 HTML**，路径 `$WORKSPACE/YYYY-MM-DD-晚餐合集.html`
   - 模板规范：`raw/misc/晚餐合集-HTML模板格式.md`
   - 配色：DK 红 `#c4452c` + 绿 `#5a7d3a`

5. **营养总览 section**（自动附加在合集末尾，见工作流二）

6. **落盘归档**：每菜 md + HTML 落盘、合集落盘、`wiki/log.md` 追加记录、输出 minis:// 链接清单、提醒同步库存

### 合集 HTML 的 12 个 section（固定顺序）

1. 🍽️ 今日菜单（menu-card + 跳转）
2. 📋 快速信息（quick-info-grid）
3. 🛒 食材汇总（去重表格）
4. ⏱️ 厨房动线（timeline，T+X 时间轴）
5. 💡 因子分析（每菜 factor-block）
6. ⚗️ 反应激活（反应-条件-效果表）
7. 🎯 预期成品（质地/色泽/风味/营养保留表）
8. ⚠️ 安全边界（callout 警示）
9. ❌ 缺口提醒（gap-list）
10. ✅ 成功关键 + ❌ 常见错误（每菜配对）
11. 🔗 相关卡片（跳转其他因子页）
12. ✅ 置信度（callout）

### 输出原则

- 尽量做在一个 HTML 里；单菜也要完整版合集，不只出分散食谱卡
- workspace 统一命名 `YYYY-MM-DD-...` 或 `{菜名}.html`
- 缺口让用户决定；配方有歧义先问

## 二、营养估算工作流（合集自动包含）

**触发**：用户报餐后自动执行；或用户说"今天吃了什么 / 能量够不够 / 估算一下"。

### 步骤（4 步）

1. **摄入估算**：每菜按标准份汇总 kcal + 蛋白/脂肪/碳水
   - 数据源：中国食物成分表（第 6 版）/ USDA FoodData，交叉验证，给区间不给假精确单点
2. **消耗估算**：直接查 `raw/misc/小豆-用户营养档案.md` 的 BMR/TDEE 预计算表；有额外运动再查 MET 表加回
   - 档案缺字段时先问一次用户并落盘，之后不再问
3. **能量盈亏**：摄入 - TDEE = 盈亏值
4. **输出（简化版，2026-08-07 用户确认）——只报 3 个数字**：
   ```
   应摄入（TDEE）：2200 kcal
   实摄入：1800 kcal
   能量缺口：-400 kcal
   ```

### 明确不输出的（用户嫌太详细已砍掉）

- ❌ DRIs 占比表 / 进度条可视化
- ❌ 加减餐建议、补救方案
- ❌ 详细三大营养素分项表、双人分别盈亏分析

### 边界

- 估算本身有 ±10-15% 误差，用户问起要说明
- 不做医学建议，不是处方
- 用户主动要详细版时可以展开，但默认只给 3 个数

## 三、食材库存同步工作流

**触发**：用户报食材变动（"买了 X"、"Y 用完了"、"冰箱里有…" + 更新库存）。

1. 读 `raw/misc/小豆-家庭食材库存.md` 当前清单
2. 计算 diff：新增 ✓ / 消耗 ✗（数量从旧 → 新）/ 过期移除 ✗
3. 列 diff 给用户确认——**不静默修改**
4. 用户确认 → 写入文件 + 追加更新日志

此工作流独立于合集生成；合集里只做对账提示，不做库存写入。

## 四、实测反馈与技能修订工作流

**触发**（满足任一）：
- 用户做完菜反馈"出问题了"（烫伤/夹生/糊锅/味道不对）
- "按你的做法没成功" / 引用具体参数的反馈（"30 秒太短"）
- 用户说"改一下" / "修订" / "更新"

### 步骤（5 步）

1. **复盘事故链**：从描述还原完整时间线（例：200°C 油锅 → 爆香料 → 直接淋醋 → 油花四溅）
2. **定位根因**：找到因子模型里缺失或被简化的因子（例：忽略「醋含水 90%」「站位防护」）
3. **影响范围评估**：这条教训波及哪些其他菜谱/技巧（例：所有含液体调料的菜）
4. **拟定修订方案**：改哪些文件、新建什么页面
5. **执行修订**：改文件 + 重新生成 HTML + 更新 `wiki/log.md` + 置信度升级

### 修订必含要素

- 物理/化学原理（为什么错，不只说"要小心"）
- 具体正确做法（"离火 5 秒"，不是"注意安全"）
- 错误示例（用户实测事故链写进 wiki）
- 影响范围（所有相关菜谱都建立交叉引用）

### 置信度与实战检验标记

| 级别 | 标准 |
|------|------|
| 高 | 多方权威一致 + Meta 支持 + 实测无翻车 |
| 中 | 单一权威来源 + 至少一次实测成功 |
| 低 | 单一自媒体/经验，无实战 |
| 实战检验 | 用户真实厨房反馈后修订（必标） |

实测后标注：`[实战检验 YYYY-MM-DD]`，证据段引用具体日期和事件。

### 给用户的诊断报告格式

```
🔍 诊断：
- 事故链：200°C → 爆香料 → 直接淋醋 → 油花四溅
- 根因：忽略了「醋含水 90%」+「站位防护」

📝 修订：
- 新建 wiki/techniques/防溅油.md
- 修订 调味料下锅时机.md + 相关食谱
- 重新生成 N 个 HTML

✅ 置信度升级：低 → 高 [实战检验 日期]
```

### 反模式

- ❌ 当孤立事件处理（必须扩展到所有相关场景）
- ❌ 只口头答应不落盘
- ❌ 改一处不留交叉引用
- ❌ 隐瞒错误只说"下次注意"

## 五、决策与取舍工作流

**触发**：用户要做任何取舍判断——买/换/选/推荐、A 还是 B、"该不该做某事"。不只是选品。

**核心逻辑已统一为通用决策模型**，完整定义见 [docs/decision-model.md](../docs/decision-model.md)，此处只给要点：

### 决策漏斗（先砍范围）
```
需求 → ①地域(国内在售) → ②预算带 → ③销量/好评TOP → ④社区榜单(找候选)
     → ⑤幸存5-10个各抓【决策关键参数】→ 跑完整思维链
```

### 思维链（每候选跑一遍）
```
① 安全 VETO（权威/循证，威胁安全直接出局）
② 价值判断（多花的钱能否换【真实体验提升】？能→买贵；不能→买便宜）
③ 频率触发器（高频+离不开才进②）
④ 信号集（参数/体验/技术/口碑 → KOL测评+评论区，靠多看，标恰饭风险）
⑤ 地域可得性（强偏好国内，跨境折损）
```

### 参数获取（决策关键参数 + 标称/实测分离）
- 先定义品类「决策关键参数表」（只抓影响真实体验的几个）
- 金字塔取证：官方→电商规格→博主实测→评论区
- **选品渠道硬门槛**：B站和小红书都必须搜；综合横评/选购建议优先，其次单品实测和长期使用。B站视频必须分别看字幕/正文与评论区；小红书笔记必须分别看正文与评论区。四格证据（B站正文、B站评论、小红书正文、小红书评论）至少三格，关键推荐尽量四格齐全。弹幕只能补充，不能替代字幕或评论区。
- 渠道不可用时标明“单渠道证据”，改用另一渠道/网页/电商评论补证，不得假装完成双渠道验证
- 评论区抽样要统计重复观点、区分高赞共识与单个极端个案，并记录送测/营销质疑
- 标称值 vs 实测值分开记，用交叉后的可信值

### 输出：完整推演决策报告
```
🧭 需求 → 📋 多角度候选方案 → 🧠 完整思维链(每角度✓/✗) → 🎯 明确推荐+备选+何时翻盘
```

### 验证层（可选）
> ⛔ 2026-09-23：原载体 MCP `llm-verifier-ug` 已停用 → 改用 **jev / TypeSafe** 做独立判断打分；姿态不变（只价值侧、分数非证据、安全不外委）
```text
思维链出结果 → 独立第二评委（jev）对候选+参数+用户标准做终审
  一致→推荐标「已过独立验证」；不一致→复查链条再定稿
  红线：只进价值侧，安全绝不外委；不可用则跳过
```

### 进化闭环（核心差异点）
```
DK 给报告 → 用户给真实思路+最终决定
  一致 → 标 [决策检验 YYYY-MM-DD]
  不一致 → 剖析差在哪 → 调整规则 → 链条进化（DK 也可反劝用户）
```

### 原则
- 就事论事：基于用户真实约束，不推通用"全网最佳"
- 缺点必须讲透 + 完整思维链展示（用户要的是推演，不是独断结论）
- 安全永远走权威，价值走 KOL+评论区，两者冲突安全压过价值
